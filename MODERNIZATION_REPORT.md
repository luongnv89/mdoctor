# Modernization Report — mdoctor

**Audited:** 2026-09-05 · **Commit:** `ace7f0a` · **Branch:** `main`
**Stack:** Pure Bash 3.2+ CLI (macOS + Debian/Ubuntu Linux) · **Size:** 70 shell files, ~7.5 kLOC source + 0.8 kLOC tests
**Baseline:** AMBER — all scripts parse and 8 of 9 test files pass, but the 9th cannot be run safely on a developer machine and there is no lint or coverage tooling installed locally

## Summary

|---|---|
| Critical | 10 |
| High | 53 |

| Low | 41 |
| **Total** | **191** |

mdoctor is a well-structured, actively maintained tool that has outgrown its own safety model. The architecture is sound — a module registry, a deliberate Bash 3.2 compatibility floor that the code genuinely honours, five CI jobs that are all green, and a real safety layer in `lib/safety.sh` with a documented error taxonomy. The problem is that the safety layer covers only one of the three module families and only some of the paths inside it. `cleanups/` routes through the guarded primitives; `fixes/` bypasses them entirely, with zero uses of the dry-run wrapper, the operation log, or the path validator across all ten modules. Every deletion call site then discards the validator's return code with `|| true`, so a module that deleted nothing and a module that was blocked at every target both report success.

Three defects stand out because they destroy data the user did not agree to lose. On Linux the "old logs" cleanup resolves its target to `$HOME/.local/share`, the entire XDG data root, and deletes every file older than seven days under it — 103,440 files including the GNOME keyring on the machine this audit ran on. No confirmation prompt exists anywhere in the product: a repo-wide search for a yes/no gate returns nothing, so `--force` deletes immediately after printing a summary that the safety documentation describes as a review step. And the project's own test suite runs `cleanup.sh --force`, which reaches `docker system prune -af --volumes` outside the test's sandbox, wired to a `pre-push` hook.

The cross-platform release is the common thread. Linux support shipped in v3.0.0 with the macOS-shaped protected-path list unchanged, macOS-only fix modules left ungated, `ping -W` used with inverted units, and the guidebook never revised. The plan sequences the data-loss fixes first, then the safety-layer coverage gap, then the platform correctness debt.

**Top 5 by impact:** `F-BUG-001` — Linux log cleanup deletes the whole XDG data root · `F-BUG-004` / `F-TEST-002` — the test suite and its pre-push hook destroy real Docker volumes · `F-BUG-003` — no confirmation gate exists for any destructive operation · `F-BUG-006` — `sudo chown -R /usr/local` runs unconditionally on Linux · `F-BUG-005` — installer and uninstaller `rm -rf` an unvalidated environment-supplied path.

The Bash 3.2 floor is **not** reported as an EOL-runtime Critical, and that deviates from the standing rule deliberately. Three conditions the rule assumes do not hold here: the project ships no Bash of its own (every script uses `#!/usr/bin/env bash` and runs on the host's), the 3.2 path executes only on macOS where Apple's vendored 3.2.57 is not something this project can upgrade, and raising the floor would break the "zero dependencies" promise on the primary platform. A full-text sweep of all 70 shell files found zero uses of any Bash 4+ construct — no associative arrays, namerefs, `mapfile`, `${var^^}`, `&>>`, or `coproc` — so the constraint is genuinely respected rather than merely declared. The W3 task is to document the floor and its banned-construct list, not to upgrade anything.

## Cross-cutting patterns

Findings that recur rather than sit at one line. Each names the finding IDs it generalizes.

- **The safety layer covers `cleanups/` and not `fixes/`.** All ten fix modules use zero of `run_cmd_args`, `op_record`, `safe_remove` and `validate_deletion_path`, so `mdoctor fix` has no dry-run, no pre-flight, no confirmation and no audit trail, while `mdoctor clean` has all four. One fix module even sets the dry-run flag to false and then deletes (`F-BUG-006`, `F-BUG-014`, `F-BUG-015`, `F-CLEAN-006`, `F-TEST-003`, `F-DEAD-018`).
- **Guards fail open — 30 sites.** All 24 deletion call sites discard the safety layer's return code with `|| true`; every fix module suppresses stderr and prints unconditional success; the dry-run gate accepts only the exact string `true` and executes for real on any other value. A module that was blocked at every target and a module that freed 40 GB are indistinguishable to the caller, the operation log and the exit status (`F-BUG-010`, `F-BUG-014`, `F-BUG-015`, `F-BUG-021`, `F-BUG-029`, `F-BUG-031`, `F-CLEAN-014`).
- **The correct pattern already exists in-tree and was not applied at the site that matters — 25 sites.** Allowlist dispatch exists for cleanups and fixes but not checks; `-print0` is used in the safety library but not in the one loop that feeds a delete; `mktemp` is used once and fixed `/tmp` names nine times; the hardened `du` wrapper was applied to two of ten sites; the platform branch is implemented in one check module and omitted in five (`F-BUG-007`, `F-BUG-008`, `F-BUG-011`, `F-BUG-012`, `F-BUG-015`, `F-BUG-039`, `F-SEC-006`).
- **Deletion guards validate a string, never a resolved inode.** No path is canonicalized anywhere; the protected list mixes exact and prefix rules inconsistently; the whitelist matches lexically so a doubled slash defeats it; and the children primitive follows a symlinked argument through to a protected target (`F-BUG-002`, `F-BUG-013`, `F-BUG-020`, `F-SEC-004`, `F-SEC-005`).

- **Pure-Bash string work delegated to a forked pipeline — 49 sites, measured 314x slower.** Field extraction, prefix tests and whitespace trimming all shell out where `read`, `case` and parameter expansion would do the same work with no fork (`F-PERF-009`, `F-PERF-010`, `F-PERF-016`, `F-PERF-018`, `F-PERF-020`, `F-PERF-021`).
- **The same filesystem tree walked two or three times per run — 9 sites.** The force pre-flight sizes six cache trees the cleanup modules then re-walk in the same process; one macOS tree is walked three times; three separate `find` passes run over identical project roots for three patterns (`F-PERF-005`, `F-PERF-006`, `F-PERF-007`).
- **External commands that can block are uncapped — 15 sites.** One of roughly fifteen network or daemon calls has a timeout, no job in CI declares one, and the 21 check modules run strictly sequentially, so independent registry round trips serialize (`F-PERF-008`, `F-PERF-012`, `F-PERF-019`, `F-DEP-009`, `F-BUG-028`, `F-CI-009`).
- **Quality gates are declared but never enforced.** ShellCheck runs at the weakest severity band, so the entire warning tier that covers this codebase's failure mode is invisible; the hook config is never run in CI and never mentioned in any contributor-facing document; the main branch has no protection so CI runs after commits land; and there is no dependency, secret or release automation (`F-BUG-037`, `F-CI-003`, `F-CI-010`, `F-CI-017`, `F-DEP-007`, `F-SEC-018`).
- **The distribution channel is untested, unversioned and ungated.** The installer ships HEAD of an unprotected branch with no tag pin, checksum or signature; CI verifies only a local-path install on macOS; and four published release tags are never installed by anyone (`F-CI-002`, `F-CI-003`, `F-CI-004`, `F-CI-012`, `F-SEC-009`, `F-SEC-020`).

**One useful negative result.** Quoting discipline is clean. No unquoted expansion reaches any destructive command, there is no `eval` anywhere, and the one string-eval path is unreachable dead code. The danger in this codebase is target *selection*, *delimiter* handling and *guard coverage*, not word splitting — worth redirecting review effort accordingly.

## Limitations

- **One test file was not executed.** `tests/test_force_preflight_resilience.sh` runs `./cleanup.sh --force`, which reaches `docker system prune -af --volumes` outside its `HOME` sandbox. The user was asked and chose to skip it. The baseline pass rate is therefore 8 of 9 files, and the destructive chain in `F-BUG-004` and `F-TEST-002` was established by static tracing through six files rather than by observing a deletion.
- **ShellCheck is not installed on this machine.** No static-analysis pass was possible for any dimension. The lint row of the baseline is Not Assessed, and the claim in `F-BUG-037` that raising the severity band would surface real findings is argued from the lint policy line alone, not from a measured backlog. A `shellcheck -S warning` run is the first thing the plan schedules for that reason.
- **No coverage tooling exists for this project.** Every coverage figure in the `TEST` dimension was reconstructed by hand from call graphs and the CI job matrix, not measured. A module reachable through a branch that was mis-read could be more or less covered than reported.
- **Findings are Linux-weighted.** The audit ran on Arch Linux. All macOS-only code paths — the Xcode and iOS-backup cleanups, the battery, Bluetooth, USB and Homebrew checks, seven of the ten fix modules, and the `/Library` probes in `F-BUG-002` — were verified by reading the source and by probing the safety library directly, never on a real macOS system. Invocation counts and duplicate-walk claims for those paths are read off the source rather than timed.
- **Most modules were grepped, not read line by line.** Across dimensions, roughly 45 of the 53 modules were analysed by targeted pattern search for the specific defect classes each dimension owns. A module-local issue inside an unread region may be under-reported. Directory-level claims — counts, names, presence, registration — were verified for all 53.
- **Network-dependent version lookups succeeded.** Current versions for `actions/checkout`, the pre-commit hooks, ShellCheck and the `bash` Docker image were resolved against live APIs, so the `DEP` currency claims are not offline guesses. Two claims in the audit brief did not survive verification and are reported as what they actually are rather than as stated: the `bash:3.2` image is maintained, not abandoned, and neither runner label is deprecated.
- **The `UX` scope was interpreted, not skipped.** The dimension map's skip rule is web-oriented and does not fit a CLI. The terminal interface was audited as the UI, and the delegate's page-oriented lenses — mobile, touch targets, contrast, landing clarity — have no CLI analogue and were not scored. Force-mode screens were reviewed from source, since running them was prohibited.
- **`openspec/`, `.specify/` and `.claude/` were assessed by git metadata and reference graph only**, not read file by file — 129 tracked files. That is enough to establish the abandonment findings but not to review their contents.
- **Repo sync was deliberately skipped.** The tree was verified clean and level with the remote before the audit, so all citations resolve against `ace7f0a`. The `code-review` delegate's own mandatory rebase step was declined because it can modify tracked files, which the read-only contract forbids.
- **Both output files were validated twice by a fresh-context reviewer.** Round 1 verified all 216 `path:line` citations resolve against `ace7f0a`, re-added the severity counts, and recomputed the plan's critical path independently; it returned two must-fix items. Round 2 confirmed those corrections and found one more, since a wording fix applied here had not been propagated to the plan. All must-fix items are resolved. One `note`-level item is knowingly shipped: plan Task 13.6 stamps a phase complete six waves before Task 13.1 finishes the last outstanding phase of it, which is honest as long as that phase is marked outstanding.

- **No dimension ran inline because a delegate was unavailable.** Both invocable delegates were present and were invoked, so no reduced-depth fallback applies. The six dimensions marked `inline` in the coverage table take that path by design, because their delegates write files.
